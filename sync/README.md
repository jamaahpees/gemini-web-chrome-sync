# Chrome profile sync

The Chrome fork is named **Cookie-Editor Gemini Sync**, version **1.14.0** and requires Chrome 120+. Right-click its toolbar icon and select **Gemini sync settings**. Existing editor options are unchanged.

Pairing explicitly requests optional access to the entered HTTPS `*.ts.net` hostname and Google/Gemini cookies. Chrome host match patterns omit ports, granting that exact hostname across ports; fetch validation separately restricts the endpoint to default HTTPS or 8443. Use the private Serve endpoint `https://your-node.your-tailnet.ts.net:8443`; port 443 on that host is an existing public Funnel. Enter an origin only (port absent or exactly 8443; no credentials, path, query or fragment). Supply the server's one-time code. Each regular Chrome profile stores its own bearer token in `chrome.storage.local`, restricted to trusted extension contexts. Incognito workers do not initialize sync.

Only allowlisted Google session cookies matching `.google.com` / `google.com` or Gemini itself are read, using the default regular cookie store and the Gemini URL. Partitioned cookies and paths other than `/` are excluded. Standard cookies retain their original secure/httpOnly metadata; `__Secure-` cookies must be secure. The allowlist includes `COMPASS` and `__Secure-BUCKET`. Cookie values and tokens never appear in this UI or sync logs; snapshots are neither persisted nor sent through extension messaging. Existing editor functionality still deliberately reads/displays cookies independently.

Changes debounce for five seconds, with an alarm fallback if Chrome suspends the worker. Status polls every minute; reconciliation runs every five minutes. Failed snapshots are re-read fresh and retried with durable, increasing sequences after 1, 2, 4, then at most 5 minutes. Chrome alarm timing is best effort, especially while the browser/device sleeps. The worker recreates missing periodic alarms without resetting existing deadlines on every wake.

HTTP authorization failures block automatic sending. The server's `account_changed` blocks nonempty snapshots until the pairing is deliberately revoked and recreated, but still permits canonical logout forwarding. The account-change lock remains after logout. An `invalid` snapshot is not repeatedly resent, but a changed cookie snapshot automatically recovers. Acknowledged hashes suppress unchanged reconciliation uploads; server-requested sync can force an acknowledged snapshot to be resent. Only hashes and pending sequences are persisted: retries read cookies fresh and reuse the pending sequence when the hash is identical. Logout uses an empty cookie list. The extension never confirms an account change. Revocation requires the server to be reachable; tokens are cleared locally only after successful server revocation.

Optional reload is disabled by default. Choose one existing Gemini tab and an interval of 15–1440 minutes (default 30). Only that tab is reloaded, only while inactive, and no new tabs are created. Inactive tabs can still be generating a response; enabling refresh can interrupt it. A closed or navigated tab is ignored until you deliberately select another.

Run `npm test` for the original tests plus pure helper and mocked Chrome worker tests. Browser permission prompts, real MV3 suspension and live server pairing still require manual integration testing.
